# Nenex：一种神经式个人 wiki 构想

[Nenex: A Neural Personal Wiki Idea](https://gwern.net/nenex)

> 现有的个人 wiki 或个人知识管理工具（如 Roam、Obsidian、org-mode）对这一波强大的语言与代码生成神经网络（如 GPT-4 这样的 LLM）的利用都极其有限，基本只停留在推荐相关链接、提供润色建议之类的小修小补上。
>
> 这与其说是因为神经网络能力不足，不如说是因为很难把它们整合进那些诞生于远早于 LLM 时代的文档系统范式里。
> 如果 [Vannevar Bush](https://en.wikipedia.org/wiki/Memex) 或 [Douglas Engelbart](https://en.wikipedia.org/wiki/Douglas_Engelbart) 在默认 GPT-4 级别 LLM 已经存在的前提下，从零开始设计一种作为「思维工具」的「神经 wiki」，它**会是什么样子**？
>
> 它大概不会长成现有工具的样子；现有工具采取的是一种超文本思路：由彼此引用的一组独立节点构成，并以文本文件的形式进行版本控制。
> 像把整份文档直接复制进去这种基于纯文本文件的简单办法，很快就会撞上性能上限，或者不大但也不可忽视的错误率。
>
> 一种更自然的办法，是从深度学习缩放范式里汲取灵感，把「一切都视为序列预测任务」：在这个以 LLM 为中心的 wiki 范式（**Nenex**）里，wiki 的中心不再是文件 / 节点，而是**编辑**。
>
> 不再受制于那些为了简单性而优化、又对自己通用聊天机器人模型格外护食的云服务商；你把所有操作都记成日志，用来训练**本地 LLM**模仿**你自己**，然后让系统在执行动作与批准 / 否决预测动作的执行之间来回交替。随着数据积累，LLM 学会预测的就不只是工具使用或泛化文本，而是**你的**文本——连同你独有的参考、偏好，乃至人格 / 价值观。
>
> wiki 不再表现为一组带有隐含历史的静态文件，而更像是版本控制系统或函数式编程里的那种主日志编辑历史；LLM 只是学习去预测日志中的下一步动作（为了可扩展性，会使用[「动态评估」](https://gwern.net/doc/ai/nn/rnn/2010-mikolov.pdf#page=2)微调）。
>
> 用户的一切编辑、参考文献添加、拼写检查、新词汇加入、摘要生成、过时页面更新等，都只是更多可供 LLM 即时学习预测的动作。它可以灵活使用[词嵌入](https://en.wikipedia.org/wiki/Word_embedding)与检索、简单的外部工具（例如下载研究论文），并通过 API 操作。
> Nenex 的 LLM 可以通过在 Nenex 日志上训练新模型而轻松升级，再额外喂给它所有相关信息（私有或公开），并吸收来自用户的任意反馈。
>
> Nenex 会以交互方式逐渐贴合用户的写作风格、知识与现有语料，并启用其他系统不具备的语义功能，比如：在个人 wiki 中找出那些因为其他页面更新而需要同步更新的页面。

截至 2023 年 9 月，LLM 已经彻底改变了我的代码写作，但我不得不承认，它们并没有彻底改变我的自然语言写作——作为 Gwern.net 工作的一部分，我只是在一些不太起眼的地方把 LLM 接了进来，比如处理恼人的格式任务（例如把 LaTeX 数学表达式转成 HTML + [Unicode](https://en.wikipedia.org/wiki/Unicode)），或者用来做注释的向量检索（你在 Gwern.net 大多数弹窗里的 `similars` 标签页都能看到）。
有时我也会把一篇随笔丢给 GPT-4 或 Claude-2，让它们提一些不错的建议。
但这并不算多么惊人。
如果 LLM 能做的，只是实现那些我能在聊天框里较为无摩擦地表达出来的短小代码需求，而其他一切还都得我亲自做，那我就实在没法从它身上榨出太多价值。

# 背景：没有生命的语料库

> ……写作与绘画有一个奇特的共同点。
> 绘画的子嗣站在那里，仿佛活着一样；可一旦有人向它们发问，它们就会极其庄严地保持沉默。
> 文字也是如此。
> 你会以为它们像是懂得自己在说什么，但如果你就某句话继续追问、想知道更多，它就会永远只重复同样的意思……它总需要父亲的扶持；独自一人时，它既不能自卫，也不能自己支撑自己。
>
> 「苏格拉底」，[Plato 的 _Phaedrus_](https://en.wikipedia.org/wiki/Phaedrus_(dialogue))

与编程相比，写作最让我沮丧的一点，是它竟如此**惰性**。
写作**并不会做**任何事；你一写，文字就只是不断堆积。
那些文字里表达出来的想法当然会彼此连接、相互构筑，但写作过程本身却丝毫不会因此改变：不管你已经写下几百万字，每一次面对的依然是同一张空白页面、同一个闪烁的文本光标。
不管你已经多少次把笔记收拢成一篇文章、扩展出一个提纲，或者跑一遍拼写检查，下一次所需的工作量还是一样；即便是像 [Emacs](https://en.wikipedia.org/wiki/Emacs) 或 [Scrivener](https://en.wikipedia.org/wiki/Scrivener_(software)) 这样最花哨的文本编辑器，帮助也很有限。
（部分原因在于，许多功能——尤其是快捷键——带来的收益，还不如你学习、配置、记住如何使用它们所要付出的努力。）

其他形式也是如此，比如期刊。
无论一份期刊多么著名、多么有影响力，它都只和最新一期一样有价值，而作为一个组织与语料库的期刊本身，价值却低得惊人。
例如，像 _Time_、_Life_、_Newsweek_ 这样的杂志，几乎在互联网出现后一夜之间就变得不值钱了；如今挂在这些品牌名下发布的内容，不过是当年那些震动世界的庞然巨物的苍白残影。
不管曾有多少杰出作家将一生奉献给它们，不管它们的报道积累多么浩瀚，也不管它们的档案库（颇有意味地被称为[「停尸房」](https://en.wikipedia.org/wiki/Morgue_file)）有多大——它们都被贱卖得几乎像白送。
写作本身、编辑、技术设备、印刷机、文化——如今全都不值钱了。
（那些残余价值里，相当大一部分其实反映的是它们摄影档案对 Getty Images 这类图库巨头的知识产权授权价值。）
没有什么比昨天的新闻更没用。

可问题又在这里：为什么会这样？为什么几十年写作积累下来的智慧没有更有用？

到底是什么，让像写作这样的智识劳动里几乎没有多少「基础设施」或「资本」，以至于你不可能「把一个新实习生插到 _Time_ 里」，然后他就立刻变成一个优秀得多的记者？
为什么一个世纪报道所凝聚的 _Time_ 之精神、那种 genius loci，不能附身在某个实习生身上，把海量知识、新闻编辑部的一切诀窍，以及诸如去哪里翻死人旧账、如何读出一个撒谎政客藏起来的暗示之类的技能，全都灌进他体内？

答案显然是：这一切不是被锁在另一个人的脑子里（而那个人多半早就不在了），就是死气沉沉地埋在一堆死树做成的纸里。
不管那个语料库变得多么庞大，不管里面埋着多少珍宝，它依然什么都不做，也永远不会替自己说话；而我们也没有任何工具，能把它悬浮起来。^[为什么关于写作的讨论总爱纠缠像牛津逗号这样琐碎的事？因为一谈到写作工具，我们就被迫只敢在路灯底下找钥匙——它们与其他媒介相比，至今仍然粗陋而贫乏；如果我们能像在图像生成里那样，为写作创造出对应的嵌入，又有谁还会浪费时间争论 tab 还是空格，而不是去试验诸如把 Shakespeare 的风格和 Sophocles 的语义混在一起这样的事？]

我想要的是：让**我那死去的语料活过来，让它能够学习、思考、写作**。

# 我想要的：真正的写作助手

LLM 确实方便，但也就方便到这里了。
如此惊人的强大技术，我居然几乎没怎么真正用起来，这让我很失望：这些东西明明就是装在盒子里的大脑，几乎都能替我写文章了！
应该存在比现在这些更有用的写作 LLM 工具——就像写代码那样，GPT-4 已经迅速变成了我快速写代码、审代码时不可或缺的工具。^[我会写 R、Python、[Haskell](https://en.wikipedia.org/wiki/Haskell)、Emacs [Lisp](https://en.wikipedia.org/wiki/Lisp_(programming_language))、[Bash](https://en.wikipedia.org/wiki/Bash_%28Unix_shell%29)、CSS、JS……其中一些我也许能真正精通，但不可能全部精通。至于要不要让 LLM 帮我写点代码、生成测试用例或文档，我从不怀疑这值不值。（具体用途可见[我关于 GPT-4 编程的技巧](https://gwern.net/tla#effective-gpt-4-programming)。）]
但看起来，并没有哪种写作工具真的走得更远。^[不过，由于大量神经网络调用的成本迫使这类工具往往藏在付费墙后面，我对这个判断并没有太强信心。也许 OA API 的一些用户，比如 [Harvey](https://www.harvey.ai/) 或 [Sudowrite](https://www.sudowrite.com/)，已经做出了很厉害的写作工具，只是我没见过。]
至少，像 Roam、Obsidian、org-mode / Logseq 这些流行写作工具，看起来都没有在真正深层的意义上把 LLM 融进去。^[顺带也可以指出，像 LangChain 或 AutoGPT 这样的「AI agent」框架，似乎也没有稳定出任何特别令人信服的 LLM 使用抽象。]

并不是说，传统「思维工具」体验里没有大把事情可以被 LLM 改善。
比如，标签管理就是一个经久不衰的痛点：给页面或 URL 加标签、把膨胀失控的标签拆开、给新的子标签命名……这些全都是极其枯燥的杂务，最后会让用户索性放弃打标签，但其实又都可以借助 LLM 的嵌入 + 卡片方式[相当直接地自动化](https://gwern.net/design#future-tag-features)。
给短页面命名、拟标题，本身就是一种会打消人创建页面念头的麻烦事。
把一篇长文拆成一套有用的层级标题，也并不是你窝在床上抱着笔记本最愿意做的事。
再比如，要给这一切写出像样的修订 / patch 摘要——烦死了！^[这也是为什么像 Microsoft Word 或 [Google Docs](https://web.archive.org/web/20100626203929/http://googledocs.blogspot.com/2010/06/optical-character-recognition-ocr-in.html) 这样的系统，通常连要求用户去描述一组改动都懒得做，尽管它们其实可以把所有编辑记录到按键粒度。当然，这也让这些日志对后来试图理解文档历史的人来说，价值大打折扣。]

# 写作助手的局限

> 「Ginny！」Weasley 先生目瞪口呆地说。「难道我教你的都白教了吗？我平时总怎么说来着？凡是会自己思考的东西，只要你看不见它把脑子藏在哪里，就永远别信它。」
>
> _Harry Potter and the Chamber of Secrets_，J. K. Rowling

但要看出 LLM 深度整合的障碍，其实并不难。
第一个问题就是：你究竟要怎么把你的文本**放进** LLM，才能让它对文本做点什么？
你立刻就会撞上一个问题：大多数 LLM 的使用方式都只能接受少量文本（通常只是一篇文章的一小部分），而且只是暂时的——一旦这次请求结束，那段文本就会被忘掉。
这就意味着，LLM 对你个人 wiki 的其余部分一无所知，更不用说那些规模更大、但明明会非常有用的可行文本数据集了。
（例如，一个 LLM 个人助手如果能学习你所有邮件与聊天记录、你读过的每篇论文或网页文本，显然会受益巨大。）
你也没法更新 LLM：如果你能把 LLM 助手犯过的每一个错误（比如把一个新名字或新术语错标成拼写错误）都汇总成一张清单，再回灌给它，那当然很好；但你也做不到，因为只要把错误与修正清单塞进输入里，它就放不下。
至于那种把你实时打字流直接喂给 LLM、借此教它理解你如何思考与修改文本的想法，也可以直接忘了。

往 LLM 里塞东西，这件事本身就是如此巨大的障碍，以至于大多数用法最后都绕着同一个问题打转：怎样把一个大型文本语料切碎，既别太容易出错，又能喂进去一小口文本，再拿回一点有用结果，然后盲目地插回语料里。
（而且，正因为这种东西不可能特别有用，它们就必须极其便宜，于是很多时候人们干脆连做都懒得做。）

我们还有安全问题：我们的 LLM 助手太容易变成一个[「迷惑副手」](https://en.wikipedia.org/wiki/confused_deputy)，执行的是攻击者通过提示注入塞进来的命令，而不是我们自己的命令，因为两者**看起来**实在太像了；而我们的 LLM 助手对我们本身又了解得太少——如果「我们」命令它删掉所有文件，它凭什么知道那绝不是我们会做的事？
它只是被训练成「乐于助人」，却没有任何关于它究竟该对**谁**有帮助的具体信息。

# 动态评估

> 落笔之手既已写下；而既已写下，\
> 便继续前行：纵有你的虔诚与机智，\
> 也无法把它诱回，去抹掉半行字，\
> 也无法让你的泪水洗去其中一个词。
>
> Edward FitzGerald（第 `51` 首，_Rubáiyát of Omar Khayyám_）

LLM 最大的问题，是注意力这一处理瓶颈限制了它从任何语料中灵活学习的能力。

我们**可以**等待更好的[注意力与记忆机制](https://gwern.net/doc/ai/nn/transformer/attention/index)。
这是一个研究热点；而像 Claude-2 这样的可公开访问模型，截至 2023 年 9 月，已经能吞下多达几十万 token。
也许神经 wiki 等待的就是这个？或者再对检索做一些改良？

但 Claude-2 仍然极其昂贵，注意力机制似乎也经常失效或导致胡编乱造；而且，一个在几十万 token 上运行的 Transformer，如果它必须为每个输出 token 都重处理整段输入，那么它天生就会很慢。
而我们想要的是数百万、乃至上千万 token，同时尽量少做那些花哨的架构工程——真正的 LLM 极繁主义者想用来编程神经网络的，不是代码，而是数据（而且还是已有数据）。

如果我们把目光回望到深度学习历史上那个如今几乎被遗忘的 RNN 时代，就会发现，除了上下文窗口之外，其实还有另一条路。
只要我们放下那个平时几乎默认不说出口的前提——即你**必须**使用无法在提示词之外实现个性化的无状态 API 调用——微调这个想法就会显得再自然不过。
神经网络模型参数量如此过剩，权重里还储存着海量已记忆事实，所以用户写下的任何东西、或者他们的参考资料库，模型都完全装得下——毕竟它们训练时一般都看过数十亿乃至数万亿 token，那再多几百万又算什么？
大型神经网络的样本效率还在不断提高：它们能从更少的数据点里学到更多，经常是一边记忆一边泛化；实际上，它们有时甚至只看一遍文本就能记住。
而微调也不必是一次性的，更不必局限于那种用户睡觉时在后台离线跑一夜的批处理流程。

当 [RNN](https://en.wikipedia.org/wiki/Recurrent_neural_network) 的用户想在一份新文本语料上拿到尽可能好的性能时，他们会怎么做？
他们会使用[**动态评估**](https://arxiv.org/abs/1308.0850)（[Transformer 版本](https://arxiv.org/abs/1904.08378)、配合 [w](https://arxiv.org/abs/2310.10638#facebook)/[retrieval](https://arxiv.org/abs/2305.18466)）^[动态评估与[「神经缓存」](https://arxiv.org/abs/1612.04426#facebook)配合得很好，而它在 Transformer 里的对应物有 [Transformer-XL](https://arxiv.org/abs/1901.02860) 与 [Compressive Transformers](https://arxiv.org/abs/1911.05507#deepmind)（以及某种程度上的 [Memorizing Transformers](https://arxiv.org/abs/2203.08913#google)）。]：本质上，就是让模型在每个时间步上对每个输入到达时都进行微调（用普通的[「在线」](https://en.wikipedia.org/wiki/Online_machine_learning) [SGD](https://en.wikipedia.org/wiki/Stochastic_gradient_descent)）。^[尽管这个方法既简单又古老，但我并不知道有什么服务真的在用动态评估。]
（举个例子，一个 char-RNN 也许会先预测下一个字符，接着收到真实的下一个字符，做一次 [backprop](https://en.wikipedia.org/wiki/Backpropagation) 更新，然后再把当前隐藏状态送进已更新权重的 RNN，去预测再下一个字符。）
这让模型得以从最新数据中学习，而且这种学习方式远比仅仅把数据放进上下文窗口、做 in-context / meta-learning 来得更深，因为它的权重会在多个时间步里不断变化、层层叠加，最终把知识永久编码进权重中。
语言模型哪怕只在训练中见过某个样本几次，甚至一次，也可能把它记住；但它们仍然会[从训练多个 epoch 中受益](https://arxiv.org/abs/2305.16264#huggingface)，于是我们就可以鱼与熊掌兼得：既拥有聪明又会记忆的模型——事实上，我们甚至可以故意训练模型去记住庞大的事实集合，把它当作长期记忆，比如相关文档的唯一 [ID](https://arxiv.org/abs/2206.02743#microsoft)。
（关于这一范式的更多背景，可见我那份 [AUNN proposal](https://gwern.net/aunn#memorization)；它几乎把「让模型记住数据」这一路走到了极限。）

![在使用冻结模型处理大规模、时变新数据集时所面临的挑战。](https://gwern.net/doc/ai/nn/dynamic-evaluation/2023-12-31-gwern-mentalgymnasticsmeme-dynamicevaluationvsalternativeapproaches.jpg)

动态评估特别擅长把模型更新到一个相当不同的数据分布上，在恒定倍数成本内处理重复 token、稀有 / 新颖 token（或两者兼有），而且原则上还能无限继续改进。
这让动态评估比向量检索之类技术更适合高度个性化的长篇写作：因为你可能会引入许多新概念、新术语（比如「Nenex」）或新参考资料，而预训练模型可能并不知道它们，它们也未必在上下文窗口中（因为之前出现它们的地方要么在另一个文件里，要么在当前文件中离焦点太远，无论是在前还是在后）。一旦这些东西被用到，它们就会被灌进模型权重里；而未被预测到的文本越令人惊讶、越新颖，更新幅度也就越大。
在一开始，当文本仍然塞得进上下文窗口、Transformer 还能靠上下文学习时，动态评估帮助不会太大，因为它还在「预热」；但它会随着见过的文本越来越多而不断变好，而失忆型 Transformer 做不到这一点。few-shot prompting 虽然在给出足够例子后也可以[追上微调](https://arxiv.org/abs/2404.11018#google)，但它可能要吃掉成千上万个例子，并耗尽哪怕高达数百万 token 的上下文窗口，代价与延迟都极其惊人；而批量微调的 Transformer 或许也能竞争，但它只能以高度错位的时间间隔发挥作用——等它起效时，已经太晚，帮不上用户正在写的那篇文章了。

这将会是一种非常自然的个人写作助手实现方式：当把微调成本摊到高频使用上时，微调其实并不贵[^finetuning]；而用户以 token / 秒来算，打字速度并不快，所以一个足够好的 Transformer 完全可以一边被动态评估、一边跟上用户（甚至还能在[同一个 minibatch 上重复训练](https://arxiv.org/abs/1806.07353)，或回头多跑几个 epoch），于是它就能在大型语料上给出显著更好的预测。

[^finetuning]: 一个成本比较：截至 2023-10-13，Gwern.net 在 12 年写作之后，Markdown 随笔大约有 ~32,388,209 个 Unicode 字符；若把 YAML / HTML 注释引用 / 摘录也算进去（而任何理想的个人助手工具都应当涵盖这些），总计大约 ~77,423,875 个 Unicode 字符。我猜如果把 HTML 转成 Markdown，或者剥掉那些不太重要的材料（比如 YAML 数据库里那些几乎没有有用元数据、却仍占用 >70 个字符的 URL），至少还能再缩小 `20%`。

    在同一天，[OpenAI finetuning](https://openai.com/pricing#fine-tuning-models) 一个 GPT-3.5 Turbo 模型（`4k` 上下文窗口，`16k` 尚不可用）的训练价格是「`$0.0080（2023 年美元） / 1K token`」。

    所以，粗略估算一下（由于里面大部分是 Markdown 和 HTML），tokenization 的效果应该还可以，平均大约是每个 BPE token 对应 `4` 个字符，那么给整个 Gwern.net 做微调的成本大约就是 `(0.008 / 1000) * (77423875 / 4) → 154.84775`，也就是约 `$160（2023 年美元）`，或者折算到 `12` 年里，相当于每月约 `$1.1（2023 年美元）`。

    再举一个例子：这篇 Nenex 随笔的 Markdown 源文件大约是 ~`33,016` 个字符（`$0.06（2023 年美元）`），而如果把所有可能相关的注释都算进去，就是 `219,174` 个字符（`$0.44（2023 年美元）`）；于是一个基础微调成本大约就是 `252k` 个字符，也就是 `$0.51（2023 年美元）`。

    如果上下文窗口是 `4k`，也就是大约 ~`16,000` 个字符，那么这个经过微调的 GPT-3.5 Turbo 在不算注释参考的情况下，一次大概能看到这篇文章的一半；如果把注释也算进去，并假设它们之前还没被微调过（虽然大多数相关注释在我开始写这篇文章之前很久就已经写好了），那就大概得在用户推进这份最完整的 `252k` 上下文 + 写作过程时，触发大约 ~`16×` 次微调。考虑到写这么多内容至少要 `5` 个小时，那么每次针对 `16k` 字符的微调平均有 >`19` 分钟可以运行，也就是每秒 `14` 个字符。

    这只是微调的成本与时间，而不是**使用**它的成本与时间。使用这样一个经过微调的模型时，OA 的收费是：输入提示 `"$0.0120（2023 年美元） / 1K token"`，输出结果 `"$0.0160（2023 年美元） / 1K token"`。（这个价格在 2023 年 11 月大约减半了。）为了给出最佳效果与最坏情况的成本估算，我们可以假设每次都用满 `4k` token 上下文（也就是每次调用 `$0.05（2023 年美元）`），而输出则是 `<$0.02（2023 年美元）/1k token`；不过平均输出到底会有多长并不清楚，而且 `1k` token 也可能严重过量。（如果那相当于 `4,000+` 个字符，那已经超过这篇文章长度的十分之一了！真正有用的输出很可能要小得多，更像是重写某一小段，接近 `<0.3k token`。）

    所以，无论从成本还是延迟上看，借助云 API 做微调似乎现在就已经可行——更何况深度学习的价格下降速度，还快过 Gwern.net 规模增长的速度！

最朴素的办法，就是在文本编辑器里直接预测用户接下来要写的内容，再配上一点 tab-completion 辅助。
这没问题，但我们还可以做得更好。
既然它都能预测用户接下来输入的单词动作，那为什么不干脆预测用户的下一个动作本身？
不只是用 Backspace 改个错字，而是**所有**动作：拼写检查、写 commit message、切换文本缓冲区……

（我们在这里追求的不是「超智能」，而是「超知识」。）

## 性能

由于用户平均打字速度很慢，所以如果 LLM 已经快到足以在合理时间内给出补全，那它大概率也能同时做动态评估；如果做不到，再开始更激进地优化也不迟。

例如，可以并行运行模型：在一个地方训练模型，同时在另一个地方运行模型（两者不一定完全相同）。
像 [LoRA](https://arxiv.org/abs/2106.09685#microsoft) 这样的轻量微调方法或许会有帮助，尽管它**并非万灵药**，因为这里的问题并不是要把模型硬编码到某个预先存在的能力上，去利用大多数任务的线性性与低维性；而是要让模型记住关于用户的**一切**，理想情况下，是他们写过或读过的一切，以及来自邮件、日历等来源的全部数据——那是大量必须被记住的细碎事实，根本塞不进一个只有几 KB（哪怕几 MB）的「轻量适配器」里——所以，LoRA 用在英文 instruction-tuning 上当然没问题，但轻量微调方法并不[擅长泛化](https://arxiv.org/abs/2410.21228)或[良好扩展](https://arxiv.org/abs/2402.17193#deepmind)，而要把它做进[完全不同的另一种语言](https://arxiv.org/abs/2304.08109)里，则需要真正的微调。
纯采样模型则可以用上各种沉重的性能优化，比如[量化](https://gwern.net/doc/ai/nn/sparsity/low-precision/index)（而这通常可以很快完成）。

Transformer 模型在这种并行设置下天生就对延迟更有容忍度，因为它的大上下文窗口为训练提供了一个缓冲区；模型不必做到最新一秒也能工作，因为用户最近的行为仍会留在上下文窗口里。
只要上下文窗口还没「溢出」，上下文学习就能暂时替代动态性。

即便它真的溢出了，用户大概也很难立刻察觉这种衰减——因为只有当用户调用了某种高度依赖那段「缺口」里不可预测文本的行为，而那段缺口恰好位于上下文窗口之外、但又位于已经做过动态评估、并被持续同步过来的训练模型所覆盖范围之外时，这种衰减才会暴露出来（而上下文窗口又会被用户动作不断用相关文本重新填满）。

而训练模型落后得越多，它就越有机会使用 **n** > 1 个 minibatch，从串行训练切换到并行批训练，一口气跳回当前状态，再和采样模型做一次大的同步。
（而如果 GPU 的 VRAM 只够采样、不够训练，那么另一个训练实例也可以放在 CPU 上运行，在那里也许会有足够的 RAM 慢慢训练。）

只要用户慢下来，这个问题就会自己消失。

# 不可变性

我们可以通过后退一步来做到这一点：不只是记录用户打下的单词，而是记录所有动作。
核心对象不再是磁盘上的某个静态文本文件，而是一串动作序列。
每个文本文件，都是由用户采取的一系列动作逐步构建出来的：插入其他文件、删除单词、拼写检查、打字、运行内置函数去完成诸如排序行之类的事情……
每个动作都可以被记入日志，而 LLM 则通过动态训练来预测下一步动作。^[至于我们具体用的是**哪个** LLM，这会退化成一个实现细节，因为我们总是可以把完整日志拿去训练一个更好或更快的模型，让它追上来，然后照常继续做动态评估。LLM 终将需要知道的一切，最终都会被包含进日志里。]

这和 Lisp 路线会配合得尤其好，因为像 Emacs 这样的 Lisp 系统，很容易把所有已执行的用户动作序列化成文本形式的 [S-expression](https://en.wikipedia.org/wiki/S-expressions)，再调用 LLM 去生成一个新的 S-expression，然后解释**那个**，从而实现用户所能做的任何事。^[你当然也可以使用像 [JSON](https://en.wikipedia.org/wiki/JSON) 这样的其他文本格式，但那并没有太大意义，而且还容易把 Lisp 重新发明得很糟。]

# 模仿学习

这为「文本编辑器」给出了一个新范式。
Emacs 的世界观是「一切皆 buffer 或 Lisp 函数」，vi 的世界观是「一切皆按键」；而对神经助手来说，世界观则是「一切皆用户模仿」。
所有用户动作与状态转移都以序列形式存储，并由 LLM 预测。

此时，LLM 就成了一个通过模仿学习来训练的深度[强化学习](https://en.wikipedia.org/wiki/Reinforcement_learning)智能体，类似于 [Decision Transformer](https://sites.google.com/berkeley.edu/decision-transformer) 这一类模型，比如 [Gato](https://arxiv.org/abs/2205.06175#deepmind) 或 [Toolformer](https://arxiv.org/abs/2302.04761#facebook)。
它既是操作系统，**也是**用户：它要学的是在文本编辑器这个「环境」里预测用户动作，以达成好的状态（例如一篇高质量的文章）。

而且，因为它受到用户监督，所以它的错误会立刻被纠正，从而形成一种类似 [DAgger](https://arxiv.org/abs/1011.0686) 的自举：如果神经网络经常以某种特定方式出错，它就会在这一类错误上收到反馈，并把它修掉。
这是因为，只要某次预测不完全对，用户接下来的动作就会把它纠正回来：用户要么撤销它，然后重试直到得到正确结果；要么把那个错误响应编辑成正确响应（这甚至可以变成一种普遍习惯，也许会绑定到某个专门的 `should-have-been` 函数上，用来编辑任何可编辑对象）；要么干脆手工做对。
这些修正会以不同程度修补模型；而理想情况下，修补的不只是那个具体例子或相似错误，而是会通过学习「用户 + 语料」这个联合函数，逐步整体改进模型的响应。

由于模型是在做动态评估，这些修正会**立刻**发生，而这些改进也会**留下来**——它们不会只是从上下文窗口里消失（或是被吸进某个遥远的云端数据库里，或许明年才有机会改善一个可能会被部署的新模型）。

用户写得越多、做得越多，模型就越会模仿这些行为；于是用户会从「亲自做」逐步切换成「只负责批准」，更多工作也就可以委托给神经网络。
这种「模仿用户」的目标，也有助于缓解关于破坏或数据外泄的安全顾虑。^[毕竟，如果**用户自己**不会愚蠢到照着邮件指令去做事，而不是按下「垃圾邮件」命令，那为什么模仿他的 LLM 会这么做？LLM 会对这个特定用户的行事方式形成很强的先验，因为它是在努力**成为**这个人，而不是被迫去服从那些毫无上下文、从天而降、并且极易和他人命令混淆的指令。]

## 热启动

LLM 可以通过示范学会做很多事情，而用户也可以通过「手工演示」某个功能的方式，亲手创造新功能。
但如果 Nenex 是一张 _tabula rasa_ 白纸，用户得为每个自己想要的功能都亲自这么做，那负担就太重了（尽管「从零开始自举出你自己独特的知识库 / wiki / 编辑器」这件事本身倒也挺有意思）。

所以，Nenex 的 LLM 应该先在一个公共的「演示语料」上预训练；这是一份跑过所有标准功能演示的日志。
用户也可以把额外的演示回馈上游，用来给问题「打补丁」。^[只要那个「改进后」的答案不要过度依赖用户的私有数据——那种数据当然不能被放进演示语料里……如果能有一种办法，自动建议哪些演示值得回传上游，那就很好：比如找出那些基础 LLM 相比于 Nenex 用户那个在私有数据上做了充分动态评估的 LLM 时，错得最厉害的地方。但我一时还看不出来，怎样区分「基础 LLM 真的错了（应该回传上游）」和「基础 LLM 其实没错，只是不知道私有数据（绝对**不该**回传上游）」这两种情况。]

## 功能实现

有了这个范式，我们现在就可以通过把「思维工具」的各种目标表达成格式合适的日志条目，再让 LLM 在当前日志和 / 或提示词条件下预测动作，来实现许多目标。

1. **文本补全**依然和以前一样，只不过现在外面会包上一层某种 `insert-text` 包装。

    提议的文本补全会通过某种 GUI 或 TUI 界面呈现给用户，比如灰色虚影文本，或者列在旁边的侧栏里。（给所有 LLM「评论」单独开一个侧栏，就像流媒体网站把聊天室放在视频旁边或下方一样，大概会是 GUI 的第一版直觉实现。）

    如果用户无视这些补全建议，继续自己写，那就会自动以常规方式纠正 LLM：说明这些补全终究不是高概率项，不该被预测出来；反过来，如果用户**确实**接受了补全，也是同理。不需要额外做什么，只要照常把文本插入记录下来即可。

    - **复制 / 粘贴**：cut / copy / paste，无论是简单熟悉的形式，还是文本编辑器支持的更强大形式（例如 Emacs 的 kill-ring 和 registers），都是打字之外最常见的任务。在大多数情况下，几次按键就足以表达一切，把 LLM 扯进来并不会有帮助。

        但在更复杂的场景里，比如用户会大量使用 registers 存放多段不同的拷贝文本，并在不同时刻粘贴它们；这时，强大的文本补全就能提供同样的功能：用户先「剪下」若干段文本（而不需要显式决定存进哪个寄存器），在日志中生成若干离散原子文本片段，然后只需输入头一个词或两个词，再接受 LLM 给出的整段 tab-completion 即可。这样就避免了命名、记忆、指定单独寄存器所带来的认知开销。
    - **缩写 / 模板**：另一个常见的文本编辑器高级用户功能，是各种形式的「文本展开」：输入一个缩写，自动展开成完整单词或短语；或者输入一个 ID，自动展开成某个模板，比如套话信函。这些功能通常都会被拥有足够历史字面访问能力、并进行普通文本补全的 LLM 吸收掉，尤其是如果用户已经养成习惯，会先敲一个 ID 或关键词，再接上那段固定文本。
    - **自动链接**：对于高密度超链接文本来说，最大的麻烦之一，就是给相关地方加上链接。自动链接正好属于那类烦人的问题：过去的自动化方法不够聪明，做不到不费很多力气就把事情办对；但手工做又既太简单、也太困难。每一个链接都得先想起来、再查一遍，这会压榨本就不可靠的记忆。像 [English Wikipedia](https://en.wikipedia.org/wiki/English_Wikipedia) 这样的网站，可以指望编辑者去用专门的加链接工具，但个人 wiki 不行。而且这也不是简单设定几条 regexp / URL 配对规则就能解决的，因为那常常会误触发（或者该触发时却没触发）；即便所有文本命中都有效，也往往会造成过度链接——通常你只想给**第一次**出现加链接，不过，如果第一次出现离当前位置太远，或者读者可能没注意到，那也许你又会希望给后面某些出现也加上，这还得看上下文……

        不过，LLM 很容易记住用户曾经写过的全部超链接，也很容易理解诸如「通常只给第一次加链接」这种细腻的语境规则。而链接预测，本来就只是文本预测的一个子集。
1. **拼写检查**会通过用户运行拼写检查、或直接编辑错误单词的日志自动学会。

    和补全一样，拼写检查也会自己修正自己。如果用户拒绝某个修正建议，那这件事就会被记下来，模型也就学会去预测这种拒绝，知道那个建议并无帮助，那个词应该被保留，并原样预测出来。
1. **摘要 / 抽象**：大多数 LLM 都可以通过提示词来为文章生成摘要。

    如果事实并非如此，或者用户想要定制化摘要，那么抽象能力也可以通过日志条目来训练：把现有文章拿来，删掉摘要，在前面加上抽象提示词，在后面拼上摘要。
1. **分节**：为一篇文章设计出一套好的层级标题会很繁琐。

    这件事未必能单靠提示词解决，但可以像摘要一样训练：定义一个分节提示词，把现有文章里的分节标题剥掉，再把这些标题拼到答案端，构造成训练样本。

    它会照常在线学习：例如，用户运行 sectionize 函数，发现其中一个小节标题很糟，于是手动改掉；这样日志里就多了一个新例子——「这里有一个被用户从坏标题改成好标题的标题」——于是「什么叫好标题」这个概念，下次也就更好了。
1. **导航**动作：在不同文件之间（或者用 Emacs 的术语说，不同 buffer 之间）切换，也是另一种可以被记录并预测的动作。

    让 LLM 在文本编辑器里自主切 buffer 未必有用，但它**可以**预测一个「默认」要切到的 buffer。给定直到当前时刻为止的上下文（而 LLM 知道这些，因为它在做动态评估，并且在上下文窗口里能看见最新日志项），用户想去哪个 buffer 往往是明显的——他已经反复切过去了，或者 buffer 切换本身有一个规律循环，或者某个 buffer 里正好含有与当前段落相关的文本。

    一旦 LLM 够厉害，用户就只需要按一个很短、很顺手的快捷键，去触发「做我想做的事」。
1. **变更控制**：只要有用户样例，选择编辑并把它们总结成一个 patch 也是可以自动化的。

    用户可以指定一组编辑为某个「patch」，写一段摘要，再把它作为一条日志项「commit」进去。编辑可以表现为 diff，也可以只是指定一段日志范围，比如前 `1000` 条日志，再配上一句摘要「把今天的骑车行程写出来了」。

    这样它就变成可以用提示词驱动的功能。
1. **任意知识**都可以被包在一个不执行任何动作的空操作命令里，加进日志。

    比如说，如果我们想让 LLM 学会某些有用参考文献，可以发出某种 `download-paper https://arxiv.org/abs/2023.1234` 命令，让系统下载论文全文并把它插入日志。
    LLM 会在论文文本上继续训练，从而学到关于它的一切；于是当我们写「正如 Smith 等人在 2023 年所示，要让 doodad 完成 frobnicate 需要 `20` 块 GPU」时，它就能理解这句引用，也许还会指出 Smith 实际上说的是「`10` 块 GPU」。

    或者我们也可以把邮件、聊天记录、网页片段、键盘日志加进去。这些输入不一定有直接用途，但关于作者的知识 / 来自作者的知识越多越好。

    （由于模型是用户本地的、私有的、定制化的——只要不走 API——这就没有隐私风险。毕竟作者在发表自己的文章之前，**本来就会**自己读一遍，任何意外泄露（比如把住址发了出去）都会被看到！我们还可以注意到：给远程模型做微调，其实是一种非常强力的混淆形式；这一事实对那些担心传票与法律取证会触及训练语料的公司来说尤其有趣——如果你先把模型微调好，再把数据丢掉，那么模型就会像一个人类员工那样，保留能力 / 知识，但若想把任何信息提取出来，就必须显式去「盘问」它……）

    - **接入更好的模型**：在「任意知识」这一类来源里，有一种尤其值得强调，那就是**更大、更好的模型**。

        当我谈到用 Nenex 的本地模型，而不是远程 SaaS API 模型（尤其是昂贵的前沿 LLM）时，这并不是严格的二选一：我们完全可以**两者都用**！没有任何理由说明，本地模型不能在不确定时，学会向一个大模型请求帮助。

        我们可以把这叫作**顾问模型**。
        你只需要把最近的 _n_ 百万 token 上下文统统倒进另一个模型里，拿到输出（它会很聪明，但受限于缺乏个性化），再把这个输出放回本地模型的日志里使用，并继续训练。

        你这么做得越多，就越是在把顾问模型里的相关知识「蒸馏」进本地模型；而本地模型也会越来越学会，什么时候值得去调用顾问。
1. **学习式检索**：

    模仿学习方法的一个好处，是神经网络可以学会逼近任意复杂过程的输出，比如更大的神经网络、人类，或者自动化工具。

    一个很有用的逼近对象，就是向量检索。向量检索往往很僵硬，因为嵌入是为通用目的而生成的，结果往往是样样通、样样松。

    然而，Nenex 的 LLM 却可以学会定制化检索。它会记住相关作品的 URL，并在收到查询时主动推荐它们；而随着这些相关链接不断被插入文章，这又会变成额外反馈。

    它甚至可以学会模仿**真实**检索数据库的响应！当检索查询被执行、结果被记入日志时，这本身就是训练数据。这还可以与检索后的过滤结合起来：例如「查找与 `(retrieve 'https://arxiv.org/abs/2023.1234')` 相关的 Transformer 论文」，其中检索本身按常规向量检索方式执行，然后由 LLM 把非 Transformer 论文过滤掉，返回最终匹配的 URL_(1--n)_。这会变成一条日志项（「查找 Transformer 论文……」→ URL_(1--n)_）；到某个时候，用户只要问一句「和 `https://arxiv.org/abs/2023.1234` 有关的 Transformer 东西有哪些？」，它就会知道。

    除了它本身就有用之外，这种对嵌入检索的模仿还能帮助把更一般性的知识灌进神经网络，使它对检索材料的理解组织得更好。
1. **过时页面**：随着你不断编辑、时间不断流逝，不可避免会出现「漂移」，也就是语言层面的 [bitrot](https://gwern.net/holy-war#bitrot)。在 Nenex 里，这能解决吗？当然能。

    你只要拿这个神经网络（它已经记住了你的 wiki），让它在每一个上下文窗口大小的文本片段上运行（也许还会配上相似文本范围的检索），并给它下提示：「这段里有没有任何过时或错误的信息？如果有，就生成一个修正它的编辑。」然后每当它预测出一个编辑，就把上下文和编辑一起展示给用户；如果用户接受，它会立刻生效，而无论是否接受，这件事都会被加入日志，模型也会在其上微调，然后重新开始整站更新。

    它每做出一次编辑，或者用户拒绝一次编辑，它都会学习；于是整站就会迅速把所有过时段落更新掉。用户不可能每次改了点东西、或者过了一周，就把整站重新读一遍……但模型可以！

    你完全可以想出很多优化方式。嵌入本身定义了一张图，所以每次用户编辑某段文字时，这个迭代更新过程都可以从那段文字出发，做广度优先遍历，去寻找有哪些文本需要根据用户刚写的内容更新。（比如，你有一堆页面在记录某个软件工具，你打开编辑器写下「`1.0` 版本现在已经能处理 JSON 了」，然后所有提到「JSON」的段落都会被模型检查；模型会说：「那这一页写着『这个工具不能处理 JSON』，显然已经过时了，我们来问用户要不要做一个 `[−not ]` 编辑吧。」）
1. **评论 / 批评**^[[Maggie Appleton](https://maggieappleton.com/lm-sketchbook#daemons) 建议用「daemons」这个术语，不过它们更像是一个议会，或者一支希腊合唱队。]：提示词可以在模型中唤起不同人格，以提出写作建议。

    既然 LLM 的全部能力都可用，我们就可以从任何角度向它索取写作建议与批评。用户可以把一组提示词打包成单个命令，比如 `M-x criticize-paragraph`。这些人格可以由用户指定，但也完全可以让模型自己去检索或生成一份可用清单。

    criticize 函数甚至可以在 Nenex 里被智能地只在某一段完成、而用户已经转去写下一段时才运行：如果那是一段内容扎实的段落，那就值得生成批评；但如果它只是一个很短的段落，比如一句修辞性的判断，那就可以跳过。这件事会随着用户的使用而自然发生

    - **头脑风暴**：既然我们都已经为一块 GPU 买单了，那不如顺手多做一些后台任务。评论 / 批评的一个例子，就是尝试生成新想法；比如可以做类似[「白日梦循环」](https://gwern.net/ai-daydreaming)那样的东西，检索语料中的随机碎片，试着生成新颖输出，再把其中最有希望的结果递交给用户评估。
